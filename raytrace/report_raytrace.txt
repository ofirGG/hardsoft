1. OVERVIEW
------------------------------------------------------------------------------
What it does
  A small recursive ray tracer (Callum and Tony Garnock-Jones, 2008). Each
  benchmark iteration builds a scene - 7 spheres, a checkerboard ground
  plane, 2 point lights - and renders a 100 x 100 image into a byte array.
  It measures object-oriented Python: many tiny classes, method calls,
  attribute access and short-lived objects.

Libraries
  math (sqrt, tan, pi), array (the RGB canvas), pyperf (timing harness).
  No third-party numeric code: all vector math is done by Python classes.

Data structures
  Vector, Point  : classes with x, y, z attributes (per-instance __dict__);
                   operator overloading (__add__, __sub__) and methods
                   (dot, cross, scale, normalized, reflectThrough) that each
                   allocate a new object. Point/Vector "type checks" are
                   method calls (isPoint(), mustBeVector(), mustBePoint()).
  Ray            : origin Point + unit Vector (normalized in __init__).
  Sphere, Halfspace : scene objects with intersectionTime(ray) / normalAt(p).
  SimpleSurface, CheckerboardSurface : shading (Lambert, specular, ambient).
  Scene.objects  : list of (object, surface) tuples; Canvas.bytes: array('B').

Algorithm
  For each pixel a primary ray is built from the camera basis. rayColour()
  computes intersectionTime() against every object, picks the nearest hit
  with t > -EPSILON, and shades it: one recursive reflected ray (depth <= 3),
  plus, for each of the 2 lights, a shadow ray tested against every object
  (_lightIsVisible). Ray-sphere test: cp = c - p, v = cp.d,
  disc = r^2 - (cp.cp - v^2), t = v - sqrt(disc) if disc >= 0.
  Per frame (measured): 25,931 scene queries - 15,265 nearest-hit
  (10,000 primary + 5,265 reflected) and 10,666 shadow queries - giving
  179,457 sphere tests and 25,501 plane tests.

2.4 Flame graph
    results/flamegraph_original.svg. Ubuntu's python3-dbg has no frame
    pointers, so the flame graph comes from a separate recording with DWARF
    unwinding (perf record --call-graph dwarf -F 199); its percentages differ
    slightly from the -F 999 report above.
    Unlike nbody, the samples do not sit in one Python frame. They are spread
    over up to 11 levels of nested Python calls below the benchmark's entry
    frame (69 % of the self time is 4-8 levels deep): the render loop calls
    the shading code, which calls the intersection tests, which call the
    Vector methods. Each Python call adds its own band of C call machinery
    (_PyEval_Vector, call_function, _PyEval_MakeFrameVector, frame_dealloc).
    Next to it are object construction frames (type_call,
    _PyObject_MakeTpCall, subtype_dealloc, dict_dealloc). PyNumber_Subtract
    alone covers 23 % of the graph, because `a - b` on Point and Vector
    objects dispatches to the Python methods Point.__sub__ and
    Vector.__sub__. The result is many narrow towers with no single dominant
    hot path: "death by a thousand small calls".

2.5 Bottlenecks identified
    B1. Method-call overhead of tiny vector methods (dot, __sub__, scale,
        mustBeVector, isPoint) - ~ 10 % in call machinery alone.
    B2. Attribute lookups through per-instance __dict__ (~ 10 %).
    B3. Temporary Vector/Point objects (452K per frame).
    B4. Redundant work: the shadow Ray is rebuilt for every object, and
        Checkerboard.baseColourAt computes a scaled vector it never uses.
    B5. The ray-vs-scene search itself (intersectionTime over all objects for
        every ray) - the core computational kernel, targeted by hardware.


3. OPTIMIZATIONS  (src/optimized.py)
------------------------------------------------------------------------------
O1. __slots__ on Vector, Point, Ray, Sphere, Halfspace  (B2, B3)
    Attributes are stored in fixed slots accessed through a descriptor
    instead of a per-object dict: faster loads/stores, smaller objects,
    cheaper allocation.

O2. Inlined vector math on the hot paths  (B1, B3)
    Sphere.intersectionTime, Sphere.normalAt, Halfspace.intersectionTime,
    Ray.__init__ (normalization), Ray.pointAtTime, the primary ray setup in
    render(), the reflection in colourAt() and the Lambert term are written
    on scalar components. No temporary Vector objects and no
    isPoint()/mustBeVector() calls remain on those paths. Every expression
    keeps the original operand order, e.g. dot = (x*x') + (y*y') + (z*z'),
    so all floating-point results are unchanged.

O3. Loop-invariant hoisting in _lightIsVisible  (B4)
    The shadow ray depends only on the light and the hit point, so it is
    built once per light instead of once per (light, object): 8x fewer
    Ray constructions (and sqrt calls) for shadow tests.

O4. Fused nearest-hit search in rayColour  (B1, B3)
    The list of (object, t, surface) tuples plus firstIntersection() pass is
    replaced by one loop that tracks the nearest hit, using exactly the same
    acceptance and tie-breaking rule (t > -EPSILON, strictly smaller wins).

O5. Small items: radius^2 precomputed per sphere; math.sqrt bound to a
    global; bound methods (rayColour, canvas.plot) hoisted out of the pixel
    loop; the unused scaled vector in Checkerboard.baseColourAt removed.

Correctness: src/check_correctness.py renders the benchmark scene with both
versions and compares the raw canvas:
    OK: 100x100 image is byte-identical (30000 bytes)

5. HARDWARE ACCELERATION PROPOSAL  -  ray_sphere_accel
------------------------------------------------------------------------------
5.1 Target component and justification
    After software optimization the sphere search is 53.3 % of the frame
    (Amdahl f = 0.533 -> at most 2.14x more from accelerating it). It is a
    pure, fixed sequence of binary64 operations (8 mul, 10 add/sub, 1 sqrt
    and 2 compares per sphere) over a small table (7 spheres) that
    does not change during a frame, and it is called 25,931 times per frame
    with the same table - ideal for a unit that keeps the table on chip and
    receives only the ray. Ray-object intersection is also exactly what
    commercial GPUs accelerate with dedicated RT cores, so the unit is not
    specific to this benchmark.

5.2 Inputs / outputs and interface
    Bus           : 64-bit memory-mapped slave (AXI4-Lite-style), level IRQ.
    Clock         : single clock, target 100 MHz on an FPGA (single-cycle
                    binary64 add/mul); ~400 MHz in a 28 nm ASIC.
    Data format   : IEEE-754 binary64 (same results as the Python code).
    Register map (word addresses):
      0x000 CTRL     W   bit0 start, bit1 mode (0 nearest-hit, 1 any-hit)
      0x001 STATUS   R   bit0 busy, bit1 done
      0x002 NSPHERES RW  number of spheres in the table (<= 16)
      0x003 TMIN     RW  acceptance threshold: -EPSILON (nearest) / +EPSILON (shadow)
      0x004-0x009    RW  ray origin px,py,pz and unit direction dx,dy,dz
      0x00A RESULT   R   bit0 hit, bits[15:8] sphere index
      0x00B RESULT_T R   distance t of the reported hit
      0x00C CYCLES   R   cycles of the last query
      0x100+4*k+f    RW  sphere k: f=0..2 centre x,y,z, f=3 radius^2
    Inputs per query: 6 doubles + mode + threshold. Outputs: hit flag,
    sphere index (8 bit), t (binary64).

5.3 Architecture (rtl/ray_sphere_accel.v, ../common/rtl/*.v)
    Datapath: one fp_add, one fp_mul (single cycle, bit-exact IEEE), one
    fp_rsqrt (17 cycles; sqrt(x) = x * rsqrt(x)), two fp_lt comparators
    (t > TMIN, t < best_t), a 16-entry sphere table (16 x 4 x 64 bit), ray
    registers, temporaries and the best-hit register (flag, index, t).
    Control FSM, per sphere k (each micro-step issues <= 1 add + 1 mul):
      uop 0-2   cp = c - p                (overlapped with cx*dx, cy*dy)
      uop 3-4   v = cx*dx + cy*dy + cz*dz (same order as Vector.dot)
      uop 4-8   cp.cp - v*v
      uop 9     disc = r^2 - (cp.cp - v*v)
      uop 10    disc < 0 ? next sphere : start rsqrt(disc)
      uop 11-12 t = v - disc * rsqrt(disc)
      uop 13    nearest: accept if t > TMIN and (no hit or t < best)
                any-hit: first t > TMIN ends the query (early exit)
    Cost: 11 cycles for a missed sphere, ~ 32 cycles for a hit candidate.
    Measured: 78 cycles per nearest-hit query, 98 per any-hit query
    (7 spheres), i.e. 0.78 / 0.98 us at 100 MHz.

    Block diagram: hw/docs/ray_sphere_accel_block_diagram.svg

          +-------- Host --------+         +------------------ ray_sphere_accel ------------------+
          | rayColour /          |  MMIO   | Query regs (p, d, TMIN, mode) --+                    |
          | _lightIsVisible      |<=======>| Sphere table 16 x (c, r^2) -----+--> operand --> fp_add  |
          |  -> driver: write    | 64-bit  |                                 |    muxes   --> fp_mul  |--> temps
          |     ray, start, wait |   IRQ   | Control FSM (k, uop) -----------+    (uop)   --> fp_rsqrt|   cp v disc t
          |     IRQ, read result |<--------|   early exit (any-hit)                        --> 2x fp_lt -> best hit
          +----------------------+         |   RESULT / RESULT_T <------------------------------ (flag, k, t)
                                           +------------------------------------------------------+

5.4 Hardware/software interface
    Per scene (once per frame): the driver writes the sphere table
    (7 x 4 doubles) and NSPHERES.
    Per query: Scene.rayColour and Scene._lightIsVisible call a C-extension
    function intersect(ray, mode) that writes 6 ray doubles, TMIN and CTRL
    (8 posted writes), waits for done (IRQ or polling STATUS) and reads
    RESULT and RESULT_T (2 reads). The Python code keeps the ground plane
    test (one dot product) and compares its t with the hardware result, then
    shades as before. Sphere.intersectionTime is no longer called in the
    search loops.
    For a PCIe card a per-query MMIO round trip (~ 1 us per uncached read)
    would eat the gain, so the production interface batches: the host
    writes a queue of rays to DMA memory (e.g. all primary rays of a
    scanline, then all shadow rays of those hits) and the unit writes
    results back by DMA, one interrupt per batch.

    Batched front end (rtl/ray_batch_accel.v, implemented and verified)
    ray_batch_accel wraps the unchanged ray_sphere_accel core and replaces
    the per-query MMIO traffic with two 64-bit valid/ready streams - the
    interface a DMA engine (e.g. AXI-Stream DMA) presents:
      in  : 7 words per ray - word 0 bit0 = mode, then px, py, pz, dx, dy, dz
            (TMIN = -/+EPSILON is derived from the mode in hardware)
      out : 2 words per ray, in input order - {hit, index}, t
      cfg : sphere table and NSPHERES, written once per frame (same map)
    A 7-word prefetch buffer accepts the next ray while the core computes,
    and the previous result waits in an output register, so stream transfers
    overlap with computation. Handing a buffered ray to the core and reading
    the result back costs ~ 14 cycles per ray (8 register writes, start,
    2 reads, control), with no CPU involvement per ray.
    Software side: the renderer is restructured into waves ("wavefront"
    ray tracing) - all primary rays of a frame or scanline in one batch,
    then all shadow rays and reflected rays of the hits in the next batch -
    because a reflected ray can only be built after its parent's hit is
    known. Each wave is one DMA transfer in each direction and one IRQ.

5.5 Verification (hw/run_sim.sh, hw/sim_result.txt)
    tb/gen_vectors.py builds the benchmark scene with the ORIGINAL classes
    and computes, with the original intersectionTime and selection rules,
    the expected result of a 20 x 20 sub-sample of primary rays plus the
    shadow rays of every hit. tb/tb_ray_sphere_accel.v drives the unit over
    MMIO exactly like the driver above:
      458 queries (400 nearest-hit, 58 any-hit), 30 hits
      avg cycles/query: nearest-hit 78, any-hit 98
      max relative error of t vs Python original = 2.416945e-16
      PASS
    (hit/miss and sphere index match exactly; t differs at most in the last
    bit because sqrt is computed as x*rsqrt(x) instead of a correctly
    rounded sqrt.)
    The batched front end is verified with the same golden vectors
    (tb/tb_ray_batch_accel.v -> hw/sim_result_batch.txt): all 458 rays are
    streamed in as one batch and the result stream is checked in order,
    once with both streams always ready (throughput) and once with
    pseudo-random stalls on both handshakes (protocol robustness):
      batch of 458 rays (STALL=0), 30 hits
      first ray word in -> last result out: 43187 cycles, 94.29 cycles/ray
      max relative error of t vs Python original = 2.416945e-16
      PASS
      batch of 458 rays (STALL=1), 30 hits
      first ray word in -> last result out: 43190 cycles, 94.30 cycles/ray
      PASS
    The stalls barely change the throughput: the ~ 7-cycle stream transfer
    of the next ray is hidden behind the ~ 80-cycle computation.

5.6 Expected performance (assumptions stated)
    Software (optimized): 5.29 us per query, 137 ms of the 257 ms frame.
      A) SoC integration (accelerator on AXI next to the CPU, ~ 0.15 us per
         MMIO access, 10 accesses + ~ 0.86 us average compute @100 MHz):
         ~ 2.4 us per query -> saves ~ 75 ms -> frame ~ 182 ms
         => 1.41x over optimized software, 4.4x over the original.
      B1) Batched streams, one lane @100 MHz - as implemented in
         ray_batch_accel (measured cycles): per frame 15,265 nearest-hit
         queries x (78 + 14) cycles + 10,666 any-hit queries x (98 + 14)
         cycles = 2.60 M cycles = 26.0 ms of accelerator time, instead of
         137.2 ms of software search -> frame ~ 257.3 - 137.2 + 26.0
         = ~ 146 ms => 1.76x over optimized software, 5.5x over the
         original. (Assumes the CPU waits for each wave; the cost of
         writing the rays into the DMA buffer is part of the remaining
         software time. Overlapping the CPU's shading of one wave with the
         accelerator's next wave would hide most of the 26 ms.)
      B2) Batched DMA, 400 MHz ASIC, 7 parallel sphere lanes (one rsqrt
         each), estimate: ~ 25 cycles = 0.06 us per query -> sphere search
         ~ 2 ms -> frame ~ 122 ms
         => 2.1x over optimized software (Amdahl limit 2.14x), 6.6x over
         the original.
      C) Unbatched PCIe MMIO: ~ 3 x 1 us reads + writes + compute ~ 4.7 us
         per query - no gain. The interface matters as much as the datapath.
    Going beyond 2.14x requires moving more of the frame (shading,
    reflection recursion, the plane) into hardware or batching the whole
    frame - i.e. a full ray-tracing pipeline rather than an offload.

5.7 Performance / area / power / frequency trade-offs
    Area (Yosys 0.9 synthesis, ../common/synth/run_synth.sh -> summary.txt;
      both netlists pass `check -assert`):
                            LUT     FF   LUT-RAM   gates   FF bits   NAND2-eq
        ray_sphere_accel   17544   1575    512     74232    5671     131.5 k
        ray_batch_accel    18348   1848    321     75422    6329     136.5 k
      * Generic gates: 131.5 k NAND2 equivalents for the single lane - about
        half FP units (two 53x53 multipliers, one inside fp_rsqrt, two adders,
        two comparators), and 5,671 flip-flops, most of them the 16-entry
        sphere table (4 kbit). In 28 nm: ~ 0.08-0.09 mm^2.
      * The batched front end costs only + 5 k NAND2-eq (+ 4 %): the 7-word
        prefetch buffer and the result registers (+ 658 flip-flops).
      * Xilinx 7-series: 17.5 k LUTs (18.3 k batched); the multipliers are in
        LUTs because Yosys 0.9 does not infer DSP48 blocks. With DSP
        inference: ~ 20-24 DSP48 and ~ 5-6 k LUTs.
      * As in nbody_accel, fp_rsqrt's private multiplier and adder are a
        quarter of the area; the main units are idle while it runs, so they
        could be shared at no cycle cost.
      Option B2 (7 lanes) multiplies the FP part (~ 65 k NAND2-eq) by 7:
      ~ 0.5 M NAND2-eq, ~ 0.3-0.4 mm^2 in 28 nm.
    Frequency: single-cycle binary64 units limit the clock to ~ 100 MHz on
      an FPGA; pipelining the units (3-4 stages) and interleaving several
      rays to hide their latency would triple fmax.
    Precision: binary64 keeps the image byte-identical to the software.
      binary32 would cut multiplier area by ~ 4x and is what GPU RT cores
      use, but could change a few boundary pixels - acceptable for graphics,
      not for a benchmark that must reproduce the reference output.
    Power (estimate): ~ 0.3-0.5 W for the single lane at 100 MHz, against a
      ~ 10 W core spending 5.29 us of interpreter time per query: energy per
      query ~ 53 uJ (CPU) vs < 1 uJ (accelerator compute), so even option A
      cuts the energy of the search loop by > 10x.
    Flexibility: the table size (16), modes (nearest / any-hit) and
      threshold are programmable, so the same unit serves primary,
      reflected and shadow rays and any scene of up to 16 spheres.


6. CONCLUSION
------------------------------------------------------------------------------
  * Software: __slots__, inlined vector math, a hoisted shadow ray and a
    fused nearest-hit loop make raytrace 3.11x faster (800 ms -> 257 ms,
    -68 %), with a byte-identical image. Function calls per frame drop by
    84 %. The ablation attributes 57 % of the saving to inlining, 19 %
    each to __slots__ and the hoisted shadow ray, 4 % to the fused loop.
  * After the software work, the ray-vs-sphere search is 53 % of the frame.
    ray_sphere_accel offloads it: a binary64 FSM datapath with an on-chip
    sphere table, nearest-hit and early-exit any-hit modes, verified
    against the original Python on 458 queries (t within 2.4e-16).
  * ray_batch_accel adds a streaming (DMA-style) front end with a prefetch
    buffer, verified on the same 458 rays with and without stream stalls:
    94.3 cycles per ray with no per-ray CPU work. Synthesis (Yosys): ~ 132 k NAND2
    equivalents (~ 0.09 mm^2 in 28 nm) for the core, + 4 % for the batched
    front end.
  * End-to-end gain: 1.4x over the optimized software with per-query MMIO
    on an SoC (4.4x over the original), 1.76x with the implemented batched
    lane (5.5x over the original, from measured cycles), and up to the
    Amdahl limit of 2.1x (6.6x over the original) with parallel sphere
    lanes. The analysis also shows that an unbatched PCIe interface would
    erase the benefit.
